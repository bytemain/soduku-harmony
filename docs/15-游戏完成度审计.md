结论：这是有真实算法和主游戏流程的原型，距离可靠的首发版本还差一轮收尾。主要问题不是缺少排行榜、成就等扩展功能，而是现有的续玩、撤销、结算、导入和重玩存在断点。原 `docs/13` 中若干“90% / 100%”不能作为验收结论；例如 AI 对话教练已经没有页面入口，历史“重玩”也不总能重现原题。

本报告依据源码调用链、直接编译纯 `.ets` 模块后的本地执行，以及从 `GamePage.ets` 提取原业务方法进行的模拟验证。模拟只替换 UI、存储和平台服务；不证明 ArkUI 响应式、触摸事件、设备性能、权限或后台行为已经正常。DevEco 构建、Hypium 与设备验证由本轮主审计另外记录。

本轮真实工具链验证补充：DevEco 26 / SDK 26 下，Debug HAP 和 Release APP 均能成功构建（未签名）。Hvigor 调用 Previewer 执行原有测试 **342 项，341 通过、1 失败、0 Error、0 Ignore**。因此项目不是“根本编译不出来”，也不能写成“测试全部通过”。测试命令虽然返回 0 并显示 BUILD SUCCESSFUL，测试报告仍有失败，必须检查报告内容。证据：[构建日志](audit-2026-11-02/native-debug-build.log)、[测试日志](audit-2026-11-02/native-unit-test.log)、[测试结果](audit-2026-11-02/native-unit-test-result.txt)。

基线唯一失败是 `VariantConfig.test.ets:336` 的 `buildKillerBoardDecorations_suppresses_grid_lines_for_cage_cells`，期望灰线宽度 -1、实际 0。`BoardDecoration.ets:189-201` 同时为该侧提供 1.5 的彩色笼边，`SudokuCell.ets:184-200` 用彩色边替代灰线；该测试只提供 `[0,1,2]` 的部分笼样本。源码与测试在同一 `57ca055` 提交内表达了互相冲突的期待，不能仅凭这个失败断言棋盘渲染损坏。后续整改按当前绘制策略扩展了边界和渲染接线回归，细节见报告顶部整改状态；最终视觉仍须手机截图验收。

## 首版必须修复

### 1. 生成未完成时返回，写入空题存档

**P1，源码控制流确认 + 原方法模拟验证。**

复现步骤：启动 9×9 新局，在生成界面按返回；或者让 Worker 创建/生成失败返回首页；随后点击“继续”。

`GamePage.ets:698` 在 loading 时允许返回；`:690` 与 `:713` 的保存判断只有“未完成”，没有“已初始化”；初始 `GameState` 是 81 个空格、空 solution。`:404` 恢复时只检查格子数，81 个空格也被当成有效局面。执行原 `saveCurrentGame()` 得到 `cells=81, solution=0, clues=0`。

应让未初始化页面不写存档，并校验恢复数据的题面、解、尺寸和变种完整性。新局真正生成成功前，也应保留上一份有效存档，而不是在 `Index.ets:588,616,629` 先删除。

### 2. 题库“进行中”不能从关卡继续；首页继续又丢失题库关联

**P1，源码调用链确认。**

复现 A：题库第一题填几个数 → 返回题库 → 点击标为“进行中”的同一题。`PuzzleLibraryPage.ets:147` 总是传原始 `puzzle81`，未传续玩数据；`GamePage.ets:403` 只有 `resumeSave` 才恢复。于是每次从题库点进都从头开始。

复现 B：题库第一题填几个数 → 返回首页 → “继续” → 完成。首页 `Index.ets:302` 只传难度与 `resumeSave`；`GameSaveData` 没有 `libraryId/puzzleIndex`，`:393` 也只从路由读这两个字段。结果不会执行 `GamePage.ets:1511` 的题库完成回写，也不会出现下一关流程。

`PuzzleProgress.cellStates` 虽然有字段（`models/PuzzleLibrary.ets:46`），但保存进度函数 `GamePage.ets:1987` 从未填写、游戏页也不读它。应保存并恢复真实局面及关卡身份；首版至少让同一题的续玩可靠。

另外，已完成题再次打开并中途退出，会被 `saveLibraryProgress(false)` 直接改成 `in_progress`，覆盖先前完成状态和成绩（`PuzzleLibraryStorage.ets:190` 直接替换）。应把本次游玩状态与历史完成/最佳成绩分开。

### 3. 填数自动删掉的同伴格笔记，撤销不会恢复

**P1，执行提取的原页面方法确认。**

复现：在同一行两个可编辑空格 A/B 给 B 标笔记“1” → A 填 1 → B 的候选 1 自动消失 → 撤销。A 恢复为空，B 的候选仍丢失。

`GamePage.ets:1393` 只记录当前格快照，随后 `:1465` 调用 `autoClearPeerNotes` 修改其他格；`:1631` 撤销只恢复已入栈格。实测输出 `peerNote=0`，预期 `ACTIVE=1`。逻辑/答案提示的自动删候选也走相同路径。

应把填数和所有受影响候选格作为一个历史批次，再统一保存；不能只为当前格做快照。

### 4. 通关后撤销、重做会重复结算

**P1，执行提取的原页面方法确认。**

复现：填最后一格通关 → 在结算弹窗出现前或关闭弹窗后点击工具区撤销 → 重做。

`GamePage.ets:2148` 的撤销/重做禁用条件不含 `isCompleted`；`:1631/:1653` 也没有完成态防护。撤销后格子变空，但 `isCompleted` 仍为 true，普通填数已被禁止；重做后 `afterAction` 又执行胜利计数和历史插入。模拟执行输出：首次 `won=1, records=1`，撤销后 `complete=true, cell=0`，重做后 `won=2, records=2`。

应定义完成态是否允许编辑，并使结算对同一局幂等。若首版不允许通关后修改，统一禁用所有改变棋盘的操作。

### 5. 小尺寸游戏污染首页的 81 字符导入

**P1，直接执行原解析模块确认。**

复现：开始 4×4 或 6×6 → 返回首页 → 粘贴合法 9×9 的 81 字符题面。

游戏页修改全局 `GRID_SIZE/TOTAL_CELLS`，首页返回时没有恢复标准导入上下文；`SudokuFormat.ets:132` 与 `parse81String` 使用当前全局尺寸。相同合法字符串在 9×9 下成功，4×4/6×6 下均抛 `error_need_81_digits:81`。即便只重新点选首页 9×9，选择器也只是改页面字段，未立即调用 `applyGridConfig`。

这是首页导入问题；题库初始化直接存内嵌字符串，不应误报为题库初始化失败。建议让交换格式解析显式接收尺寸，81 字符格式固定按 9×9 解释，避免受上一局影响。

### 6. 分享种子和历史“重玩”不能保证同一题

**P1，直接执行生成模块确认。**

标准模式的确定性样本：

| 请求难度 | seed | 对称 | 重播题面不同格数 | 完整答案 |
| --- | --- | --- | --- | --- |
| 简单 1 | 246218396 | rot90 | 32 | 相同 |
| 困难 3 | 247403185 | none | 26 | 相同 |

`generatePuzzle` 在 `SudokuGenerator.ets:461` 通过同一个 RNG 选择对称方式，再挖洞；`:519` 的 `generatePuzzleFromSeed` 跳过这次随机数消耗，造成题面不同。脚本固定随机序列，从实际新局生成结果取 seed，再用实际重播函数比较；不是人工构造两份不同配置。

此外，seed 编码 `:379` 只有难度/对称/seed，缺少尺寸与变种。`HistoryStorage.GameRecord` 也不存原题、尺寸、变种、区域或笼子；`StatsPanel.ets:334` 重玩时默认为标准 9×9。导入题和题库题仍被写成 `difficulty:imported:0` 并显示重玩按钮，无法恢复原题。

首版应修正随机流复现，并保存足够重现的题面与配置；暂未支持的记录应隐藏重玩按钮，不能打开另一道题。

## 需要如实收窄的功能宣传

### 提示不等于完整的逻辑教学

`GamePage.ets:1699` 只接受 `digit !== 0` 的逻辑步骤。Naked Pair、Pointing Pair、X-Wing 等候选排除步骤通常为 `digit=0`，被跳过后调用 `applyDirectHint` 填答案，没有展示排除过程。算法里确有这些技巧，UI 尚未连通；本地题库验证中，进阶 3/20、困难 6/20、专家 9/15 的逻辑解算包含这类步骤。

当前无提示使用计数/限制，使用答案提示完成仍可获胜和计入最佳时间。离线休闲游戏可以选择这种规则，但如果宣传“挑战”“成绩”，应明确辅助是否影响评分。

### Jigsaw 的高级逻辑评级不可靠

`LogicSolver.ets:230,543` 的部分宫交互技巧仍使用固定 3×3，而不是不规则区域。默认 Jigsaw 区域下，`generatePuzzleFromSeed(21,HARD,NONE)` 产生唯一解题，`logicSolve` 第 27 步 PointingPair 错误删除 R4C6 的正确候选 2。

复核题面：`790510000000760500000007004050400010034006751000200970009000480000004005400001006`。

错误步骤为 `digit=0`；前 26 步单值提示正确。由于当前页面跳过候选排除，本例**没有证明用户界面会填入错误数字**，影响的是内部难度评级与未来高级提示接入。建议先把这些技巧改为基于活跃拓扑，或在 Jigsaw 禁用不适用技巧。

### 请求难度与实际难度不总一致

生成器允许重试后返回最接近的候选；Worker 回传 `actualDifficulty`，但页面 `GamePage.ets:551` 采用请求难度。样本请求专家 4，实际返回 5，seed 为 97647717。界面和统计应展示实际评级，或者明确采用宽松分档。

### 内置题库数量与说明需要更新

实际调用链：`PuzzleLibraryPage.ets:70` → `initBuiltinLibraries` → `BUILTIN_LIBRARIES` → `loadBuiltinPuzzles`，不读取旧 rawfile manifest。8 组为：入门 20、进阶 20、困难 20、专家 15、地狱 15、极简 15、对称 15、经典 15，共 135。

这些题目全部通过唯一解验证。README/rawfile manifest 的 75 题属于旧资料。不能只根据文件存在就把 rawfile 数量当成运行时题库数量。

## 首版范围与验收顺序

1. 优先稳定标准 9×9、内置题库、笔记、提示、存档、结算；修复上述六类数据/流程问题。
2. 对 4×4/6×6、3 个变种分别做实际设备验收；验证不足的模式可以暂时隐藏入口，首版不必为保留所有模式而带病发布。
3. 上架文案只写当前有入口且验收通过的功能。删除 AI 对话教练、完整高级逐步教学、回放、12/16 尺寸、已全面适配电视/手表等未经支持的描述。
4. 测试至少覆盖：生成中返回/失败、有效存档不丢失、题库中断续玩、完成题重玩不降级、跨格候选撤销、通关后操作、尺寸切换后导入、种子与历史重玩、前后台与锁屏计时。

不建议现在优先增加每日挑战、联网排行、成就或多平台壳；这些不能解决已有基础功能的不可靠。
