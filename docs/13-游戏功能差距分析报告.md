## 二、部分实现功能（⚠️ 有差距）

### 2.1 ⚠️ 错误上限（3 次机会）

**现状**：
- 错误计数已实现（`GamePage.ets` line 1153 递增 `errorCount`）
- TopBar 显示当前错误数

**缺失**：
- **无 3 次上限判定** — 无论错多少次都可继续游戏
- **无游戏失败状态** — 没有"Game Over"概念
- **无失败弹窗** — 没有"重试/返回"选项
- **无失败统计** — `recordGameLost()` 从未被调用

**影响**：降低游戏紧张感，减弱玩家对每一步的慎重程度。竞品（Sudoku.com、Andoku 3）均有 3 次限制。

**开发计划参考**：Phase 2 任务 2.4（状态标记为 ⚠️）

---

### 2.2 ⚠️ 深色模式

**现状**：
- `resources/dark/element/color.json` 颜色资源已定义
- `EntryAbility.ets` 中有主题切换逻辑
- `GameConstants.ets` 有 `applyTheme(isDark)` 函数
- SettingsPanel 提供主题切换（Light/Dark/System）

**缺失**：
- 部分组件仍有 **硬编码颜色值**（未使用 `Colors.xxx` 常量）
- 某些边框、阴影、文字颜色在深色模式下 **对比度不足**
- 变种装饰（Killer 笼子、Jigsaw 边界）的深色适配 **未测试**

**影响**：深色模式下可能出现文字看不清、边框不明显等视觉问题。

---

### 2.3 ⚠️ 变种数独 — Sudoku-X（对角线）

**现状**：
- `VariantConfig.ets` 定义了 `DIAGONAL` 类型
- `VariantTopology.ets` 可构建对角线拓扑（额外 2 个 unit）
- `PuzzleWorker.ets` 在生成时应用对角线拓扑

**缺失**：
- **无对角线视觉标记** — 棋盘上看不出哪些格属于对角线
- **无对角线高亮** — 选中对角线格时不高亮整条对角线
- **对角线冲突检测** — 验证器是否正确使用变种拓扑未充分验证

**影响**：用户选择"对角线"变种后，UI 上与标准模式无任何区别，体验混乱。

---

### 2.4 ⚠️ 变种数独 — Jigsaw（不规则宫）

**现状**：
- `VariantConfig.ets` 定义了 `JIGSAW` 类型和固定 `regionMap`
- `BoardDecoration.ets` 有 `buildJigsawBoardDecorations()` 构建边界装饰
- `PuzzleWorker.ets` 应用 Jigsaw 拓扑

**缺失**：
- **固定布局** — 只有 1 种硬编码的不规则宫分区，无法随机生成
- **边界渲染不完整** — 装饰模型已定义但 UI 组件的边界粗细适配不完善
- **无区域颜色** — 竞品（Andoku 3、SudokuPad）用不同背景色区分不规则区域

**影响**：所有 Jigsaw 游戏都是同一个分区布局，重复可玩性极低。

---

### 2.5 ⚠️ 变种数独 — Killer（杀手数独）

**现状**：
- `KillerSudoku.ets` 定义了 `KillerCage` 结构和固定笼子布局
- `BoardDecoration.ets` 有 `buildKillerBoardDecorations()` 渲染笼子边框 + 求和标签
- UI 组件可以显示笼子装饰

**缺失**：
- **纯展示模式** — 笼子仅作为视觉装饰，**不参与求解和验证**
- **无求和约束** — 同一笼子内数字之和不做检查
- **无不重复约束** — 同一笼子内数字可重复
- **固定笼子** — 横向切割的固定模式，无随机生成
- **无候选数排除** — 笼子求和信息不影响笔记候选数

**影响**：Killer 模式实际上就是带笼子装饰的标准数独，完全没有 Killer 玩法。

---

### 2.6 ⚠️ 可变棋盘尺寸

**现状**：
- `VariantConfig.ets` 预定义了 4×4、6×6、9×9、12×12、16×16 配置
- `GameConstants.ets` 有 `applyGridConfig()` 运行时切换网格大小
- Index.ets 有网格大小选择 UI（4×4、6×6、9×9）

**缺失**：
- **大量硬编码 9×9** — 组件中仍有 `81`、`9`、`3` 等魔法数字（参见 Doc 12）
- **键盘不适配** — 3×3 手势键盘在 4×4（仅 4 个数字）和 12×12（12 个数字）下不合适
- **棋盘渲染不适配** — `SudokuBoard.ets` 的 `ForEach` 循环硬编码 9 行 9 列
- **非 9×9 实际不可玩** — UI 选择后显示 "Coming soon" 提示

**影响**：UI 上提供了大小选择器，但选了之后无法真正游玩，造成用户困惑。

## 三、完全缺失功能（❌ 未实现）

### 3.1 ❌ 选关/题库系统（用户重点提到）

**这是整个应用最大的功能缺口。**

#### 现状

| 层面 | 状态 | 说明 |
|------|:---:|------|
| 数据模型 | ✅ | `PuzzleLibrary.ets` 已定义 `PuzzleLibrary`、`PuzzleEntry`、`PuzzleProgress` 接口 |
| 工厂函数 | ✅ | `createPuzzleLibrary()`、`createPuzzleEntry()`、`computeLibraryStats()` |
| 存储层 | ❌ | `PuzzleLibraryStorage.ets` 设计文档已写但未实现 |
| 内置题库数据 | ❌ | `rawfile/puzzles/` 目录不存在，无 SDM 文件 |
| 题库列表页 | ❌ | 无浏览、筛选、搜索题库的 UI |
| 题库详情页 | ❌ | 无查看每道题进度的 UI |
| 选关 UI | ❌ | **用户无法直接选择第 N 题来玩** |
| 进度追踪 | ❌ | 无法管理多个未完成的题目（当前仅单局存档） |
| GamePage 集成 | ❌ | GamePage 不识别 `source='library'` 参数 |
| 首页入口 | ❌ | Index.ets 没有"题库"按钮或卡片 |

#### 核心问题

1. **无法选关** — 玩家只能通过以下方式获取题目：
   - 按难度随机生成（完全随机，无法选择特定题目）
   - 手动粘贴 81 字符串（需要外部来源）
   - 输入种子 ID（需要知道种子）
   - 从历史记录 Replay（只能重玩已完成的题）

2. **无法浏览题目** — 没有题目列表、分类、筛选功能

3. **无法管理多局进度** — 只有 1 个存档槽位，开始新游戏会覆盖旧进度

4. **无法挑战经典名题** — 竞品（Sudoku.com 1 万+题、Enjoy Sudoku 海量题库）的标配功能

#### 与竞品差距

| 竞品 | 内置题库 | 选关 | 多局进度 | 每日挑战 |
|------|:---:|:---:|:---:|:---:|
| **Sudoku.com** | ✅ 10000+ | ✅ | ✅ | ✅ |
| **Enjoy Sudoku** | ✅ 海量 | ✅ | ✅ | ✅ |
| **Andoku 3** | ✅ 内置 | ✅ | ✅ | ✅ |
| **Good Sudoku** | ✅ 无限 | ✅ | ✅ | ❌ |
| **Sudoku Harmony** | ❌ | ❌ | ❌ | ❌ |

#### 已有基础设施可复用

- ✅ `SudokuFormat.parseSudokuInput()` — 可解析 SDM 等题库文件格式
- ✅ `DifficultyEvaluator` — 可为每道题评估难度
- ✅ `PuzzleWorker` — 可在后台线程处理批量题目
- ✅ `PuzzleLibrary.ets` 数据模型 — 接口已定义
- ✅ Seed 系统 — 可作为题目标识补充

#### 建议实施路径

```
Step 1 (2-3 天): PuzzleLibraryStorage 存储层实现
Step 2 (2-3 天): 准备内置题库 SDM 文件（至少 easy/medium/hard 各 50 题）
Step 3 (3-4 天): 题库列表页 UI（PuzzleLibraryPage）        ← 依赖 Step 1
Step 4 (3-4 天): 题库详情页 + 选关 UI                      ← 依赖 Step 1, 2, 3
Step 5 (2-3 天): GamePage 集成 library 源（进度保存）       ← 依赖 Step 1
Step 6 (0.5 天): Index.ets 添加题库入口                     ← 依赖 Step 3, 4, 5
Step 7 (3-5 天): 外部题库下载（HTTP）                       ← 依赖 Step 1, 3
```

### 3.2 ❌ 每日挑战

**现状**：完全未实现

**需要的组件**：
- 日期种子生成器（`Date → seedId`）
- 每日挑战页面 UI
- 打卡日历组件
- 连续挑战记录
- 可选：在线排行榜（需服务端）

**种子基础已就绪**： `SeededRandom` + `generatePuzzleFromSeed()` 使得同一日期全球生成同一题成为可能，实现成本相对较低。

**影响**：每日挑战是**用户留存的核心功能**。Sudoku.com 的日活主要来自每日挑战。

## 四、游戏性分析

### 4.1 核心循环

```
当前循环：选难度 → 随机生成 → 解题 → 完成/退出 → 回到选难度
                                ↑ 仅此一条路径

理想循环：
  路径 A：选难度 → 随机生成 → 解题 → 完成 → 记录统计
  路径 B：题库 → 选关 → 解题 → 完成 → 更新进度 → 下一关
  路径 C：每日挑战 → 解题 → 完成 → 更新打卡 → 查看排行
  路径 D：教学模式 → 学习技巧 → 练习 → 掌握新技巧
  路径 E：多人竞速 → 配对 → 同题竞速 → 查看对比
```

**问题**：当前只有路径 A（随机生成），缺少**目标感**和**进度感**。

### 4.2 长期留存问题

| 留存驱动力 | 当前状态 | 需要的改进 |
|-----------|:---:|---------|
| **进度感** | ❌ | 题库进度条（已完成 40/50 → 努力完成剩下 10 题） |
| **目标感** | ❌ | 成就系统（解锁下一个成就 → 持续游玩） |
| **习惯性** | ❌ | 每日挑战（每天一题 → 打卡习惯） |
| **社交性** | ❌ | 分享/排行（比朋友快 → 竞争动力） |
| **成长感** | ⚠️ | 统计有基础，但缺少技巧掌握度和进步趋势 |
| **多样性** | ⚠️ | 变种数独有框架但功能不完整 |

### 4.3 上手体验

| 环节 | 评价 | 说明 |
|------|------|------|
| 首次启动 | ⭐⭐⭐ | 简洁明了，可直接开始游戏 |
| 手势学习 | ⭐⭐⭐⭐ | 首次引导遮罩清晰 |
| 难度理解 | ⭐⭐⭐⭐ | 颜色编码 + 技巧说明 |

## 六、选关功能专项分析

### 6.1 用户故事

> 作为数独爱好者，我想从题库中选择一道特定的题来挑战，而不是每次都玩随机生成的题。
> 我希望能看到自己在题库中的进度，知道还有多少题没完成。

### 6.2 当前用户旅程（无选关）

```
1. 打开 App
2. 选择难度（简单/中等/困难/专家/地狱）
3. 点击"开始新游戏"
4. 系统随机生成题目 ← 用户无法控制生成的题目
5. 解题...
6. 完成（或退出保存）
7. 回到首页
8. 再次点击"开始新游戏" ← 又是随机题目，无进度感
```

### 6.3 理想用户旅程（有选关）

```
1. 打开 App
2. 看到"题库 (3 进行中)" 入口
3. 进入题库列表
   - 入门精选 50 题 — 已完成 40 (80%) [████████░░]
   - 进阶挑战 50 题 — 已完成 15 (30%) [███░░░░░░░]
   - 高手之路 50 题 — 未开始
4. 选择"入门精选"
5. 看到 50 道题的列表
   - #1 ✅ 02:31 0错
   - #2 ✅ 05:12 1错
   - #41 🔄 62% 03:45 ← 上次玩到这里
   - #42 ⭕ —
6. 点击 #41 继续上次的进度
7. 解题...
8. 完成 → 自动跳到 #42
9. 返回题库列表 → 进度更新为 82% (41/50)
```

### 6.4 选关功能的技术可行性

| 依赖项 | 状态 | 缺失部分 |
|--------|:---:|---------|
| 数据模型 | ✅ 就绪 | — |
| 格式解析 | ✅ 就绪 | — |
| 难度评估 | ✅ 就绪 | — |
| 存储层 | ❌ | 需实现 `PuzzleLibraryStorage` |
| 题库文件 | ❌ | 需准备 SDM 文件或使用生成器预生成 |
| UI 页面 | ❌ | 需新建 2 个页面（列表+详情） |
| GamePage 适配 | ❌ | 需识别 `source='library'` 参数 |
| 路由注册 | ❌ | 需在 `main_pages.json` 注册新页面 |

**结论**：数据模型和工具链已完备，主要缺少 **存储实现 + UI 页面 + GamePage 集成**。

## 八、总结

### 核心发现

1. **游戏核心机制（解题体验）已经非常成熟**，手势系统、三态笔记、多选操作等交互创新在竞品中独树一帜。

2. **最大的功能缺口是「选关/题库」系统**。数据模型已定义但未实现，导致：
   - 玩家只能随机游玩，无法选择特定题目
   - 无法管理多局进度
   - 无法感受到"通关进度"
   - 与所有主流竞品差距明显

3. **留存设计严重不足**。缺少每日挑战、成就系统、技巧教学等长期驱动力，核心循环过于单一。

4. **变种数独处于"半成品"状态**。框架和数据模型完备，但 UI/约束/生成都不完整，部分选项暴露给用户会造成困惑。

5. **低成本高回报的改进**：错误 3 次限制、音效反馈、隐藏不可玩选项，这些可以在 1-2 天内完成并显著提升体验。

### 建议的下一步行动

**最高优先级**：实现选关/题库系统（利用已有的 `PuzzleLibrary` 模型和 `SudokuFormat` 解析能力），这是弥补与竞品差距的最关键功能。
